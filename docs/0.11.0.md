# 0.11.0: 프롬프트 캐시 점검과 A/B 비교(show-ab)

자리를 비운 동안 진행한 작업의 판단 근거와 확인할 결정이다. 바로 고칠 수 있는 것은 반영해 배포했고, 정책으로 열어 둘 만한 것은 아래 "확인할 결정"에 모았다.

## 1. 새 세션과 프롬프트 캐시

**결론: 대부분 따로 할 일이 없다.** 단위마다 새 세션을 여는 구조가 캐시를 버리는 것은 아니다. 고친 곳은 두 군데다.

| 확인한 사실 | 근거 |
|---|---|
| 캐시 읽기는 기본 입력가의 약 0.1배(Opus 5.5는 0.05배), 쓰기는 5분 TTL 1.25배·1시간 TTL 2배 | Anthropic prompt caching 문서 |
| 캐시를 읽으면 TTL이 무료로 다시 시작된다. 수명은 요청 시작 시각부터 잰다 | 같은 문서 |
| 앞부분이 같으면 세션이 달라도 캐시를 공유한다. 새 헤드리스 세션의 첫 요청이 약 18K 토큰을 캐시에서 읽었다 | `work scout` 실측 (`cache_read_input_tokens: 18483`) |
| Claude Code 세션은 1시간 TTL을 쓴다 | 세션 환경 정보 |

- **단위마다 새 세션:** 시스템 프롬프트와 도구 정의는 단위끼리 캐시를 공유한다. 단위가 연달아 돌면 이 캐시는 식지 않는다. 새로 쓰는 것은 단위마다 다른 스킬 본문·브리핑·태스크뿐이고 수천~수만 토큰 수준이다.
- **긴 대화를 이어 쓰기:** 매 턴 쌓인 맥락 전체를 읽는다. 맥락이 커질수록 턴당 비용이 늘고, 긴 맥락은 품질도 떨어뜨린다. 1시간 넘게 쉬었다 돌아오면 전체를 2배 값으로 다시 쓴다.
- **맡김을 띄운 대화:** preflight와 실행만 한 대화라 맥락이 작다. 다시 이어 써도 비용은 크지 않다. 다만 필요한 상태는 모두 보고서·결정함·`loop.json`에 있으므로 새 대화에서 `/start-vibe`로 시작하는 쪽이 같거나 싸고, 맥락도 깨끗하다. 캐시를 살려 두려고 빈 요청을 보내는 것은 손해다.

**고친 것**

1. **작업 묶음 조정자 대기를 3600초에서 3300초로.** 0.10.0의 3600초는 1시간 TTL을 살짝 넘겨, 깨어날 때마다 조정자 맥락 전체를 2배 값으로 다시 썼다. 55분이면 캐시가 식기 직전에 돌아와 0.05배에 읽는다. 0.10.0 이전의 540초는 시간당 6번 깨어나 턴을 썼다.
2. **맡김을 띄운 대화의 안내 추가:** 실행 핸들과 함께 "돌아오면 새 대화에서 `/start-vibe`"라고 알린다.
3. **보고서 `- time:` 줄에 입력 토큰 합계와 cache read 비율 추가.** 실제 맡김에서 단위 세션이 캐시를 얼마나 재사용하는지 숫자로 확인할 수 있다.

## 2. show-ab

요청: 문제를 말하면 최소 2개, 최대 n개의 세션이 병렬로 만들고, 각자 다른 포트에서 확인한다. 디자인·UX·UI·기능·성능 무엇이든 비교한다.

**구성:** 스킬 `show-ab`(판단)와 CLI `vibe ab`(기계적인 일)로 나눴다. 브랜치, worktree, 커밋, 서버, 측정, 정리를 모델이 셸로 하면 토큰이 들고 Codex에서는 재현하기 어렵다.

| 단계 | 명령 | 하는 일 |
|---|---|---|
| 준비 | `vibe ab start <slug> --variants n` | 변형마다 `ab/<slug>/<v>` 브랜치, 형제 worktree(`../.haeram-worktrees/`, `work`와 같은 규칙), 빈 포트(4101부터). `--setup`은 의존성 설치를 병렬로, `--copy`는 `.env.local` 같은 미추적 파일을 복사 |
| 구현 | `vibe ab run <slug> --variant v --prompt-file f` | 그 worktree에서 쓰기 가능한 헤드리스 세션 하나(새 `variant` 역할, Claude/Codex). 커밋은 CLI가 변형 브랜치에 한다. 진행자에게는 summary와 view(볼 곳)만 돌아온다 |
| 보기 | `vibe ab serve <slug> --command '<dev, $PORT>'` | 변형마다 서버를 띄우고 포트가 열릴 때까지 기다린다. 실패하면 로그 tail을 보고하고 URL이 있다고 말하지 않는다 |
| 측정 | `vibe ab exec <slug> --command '<bench>' --repeat 3` | 변형을 번갈아(a b a b) 실행해 중앙값·최소·최대·종료 코드를 모은다 |
| 채택 | `vibe ab pick <slug> --variant v` | 서버를 끄고 그 변형만 현재 브랜치에 merge 커밋으로 합친 뒤 worktree 정리. 충돌이면 그대로 두고 보고 |
| 버리기 | `vibe ab stop <slug> --remove` | 서버와 worktree 정리. 브랜치는 `--prune-branches`일 때만 지운다 |

**검증**
- 테스트 283개 통과. 변형별 브랜치·worktree·포트, 미추적 파일 복사, 병렬 setup, CLI 커밋, 실제 HTTP 응답을 확인했다. 번갈아 측정, merge 부모, worktree 정리, 서버 종료, 미커밋 거절, 브랜치 보존·삭제, 뜨지 않는 서버의 로그 tail 보고도 포함된다.
- 실제 `claude` CLI(haiku)로 변형 세션 1회를 스모크 테스트했다. 12.7초 만에 `app.js`만 고쳤고, CLI가 `ab/smoke/a`에 커밋했다.

## 3. 확인할 결정

기본값은 아래처럼 정해 두었다. 바꾸고 싶은 것만 알려 주면 된다.

1. **맡김에서는 실행하지 않는다.** 고를 사람이 없어서 inbox parked로 남긴다. 다른 선택지는 맡김 중에 변형을 만들어 띄워 두고 돌아온 사람이 고르게 하는 것이다. 이 경우 서버가 몇 시간 떠 있게 된다.
2. **변형 수는 기본 2, 최대 6.** 변형 하나가 구현 세션 하나만큼의 비용이다.
3. **채택 기록은 디자인 마감과 같은 방식이다.** merge 뒤 STATE log `- YYMMDD ab <slug>: adopt <v> — <approach>`를 남기고, SSOT 규칙이 바뀌었으면 이어서 update-ssot를 한다. "문서 먼저"를 엄격히 따르려면 고른 직후 update-ssot를 먼저 하고 merge하는 순서도 가능하다. 다만 디자인 모드와 규칙이 달라진다.
4. **고르지 않은 변형의 브랜치는 기본으로 남긴다.** 나중에 다시 볼 수 있는 대신 `ab/*` 브랜치가 쌓인다.
5. **기본은 헤드리스 세션(`vibe ab run`)이다.** worktree가 프로젝트 밖(형제 폴더)에 있어서, 네이티브 하위 세션으로 하면 편집 권한 창이 변형 수만큼 뜰 수 있다.
