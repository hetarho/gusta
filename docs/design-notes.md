# 설계 노트

CLAUDE.md에서 옮긴 모듈별 설계 결정과 그 이유다. 세션마다 읽지 않는다 — 해당 모듈·절차를 바꿀 때만 그 절을 읽는다. 정본은 코드와 테스트이며, 이 문서와 다르면 코드가 맞고 이 문서를 고친다.

## 모듈
- `skills/<name>/SKILL.md` — 스킬 본문 (frontmatter `name`=폴더명, `description` 필수)
- `skills/<name>/agents/openai.yaml` — Codex 전용 메타 (Claude 설치 시 제외됨)
- `skills/gusta-create-architecture/assets/{STATE,FORMAT}.md` — 타겟 프로젝트 `spec/`에 복사되는 템플릿 (부트스트랩 정본)
- `skills/gusta-start/assets/report.md` — 맡김 세션 보고서 템플릿. `skills/gusta-start/references/`·`skills/gusta-create-task/references/lanes.md` — 작업 묶음·실행기 밖 절차. gusta-start·gusta-implement-task(태스크 단위) 본문은 loop 단위 프롬프트에 실리니 단위가 안 쓰는 문장은 references로.
- `src/verification-plan.mjs` — 선택적 검사별 실행 계획(`schemaVersion:1`, `checks`의 고유 `id`·`tier`(task|batch|ci)·`command`·`inputs`). `vibe check --plan <파일>` 또는 ARCH 검증 결정의 `plan:` 하위 줄의 백틱 JSON 경로로 연결한다. 입력을 생략하면 전체 트리를 검사 입력으로 삼으며, 명시한 입력·명령·실행 환경·범위가 같은 성공만 항목별로 재사용한다. 실패 뒤에도 성공 기록을 보존하고 실패·미실행 검사를 구분한다. 입력이 같다는 근거 없이 문서 변경을 일괄 제외하지 않는다. 수동 복구도 같은 tag·원래 마감을 잇고, 사용자 개입 시 소유한 검사 프로세스를 정리한 뒤 새 지시를 적용한다.
- `src/workspace-prepare.mjs` — CLI가 만드는 새 worktree(세션·묶음·워커·통합 후보, 모두 `.git` 밖 `.gusta-worktrees/`)에서 검사 전에 ARCH 검증 결정의 `prepare:` 명령을 한 번 실행한다. 준비 실패는 환경 실패로 보고하고 워커 수정 요청으로 돌리지 않는다.
- `src/loop-control.mjs`·`src/loop-metadata.mjs` — 단위 경계 설정 요청/receipt·소유권·독립 감시·정확한 호스트 메타데이터 journal. `skills/gusta-start/references/loop-control.md`가 제어/복구/알림 계약이다. 즉시 취소·단위 완료 정지·설정 변경을 분리하고 취소된 signal로 마감 검증하지 않는다. 보고서 밖 변경은 자동 커밋·무시하지 않는다(자기 세션 행은 조정 브랜치에 있어 작업 트리를 건드리지 않는다) — 단위가 남긴 미커밋 변경은 결과와 무관하게 로컬 ref에 스냅샷하고 HEAD로 되돌려 새 단위에 넘긴다(호스트 보고서를 건드린 단위만 멈춘다). 끝내지 못한(실패·상한 절단·`continue`) 단위는 이어가기→쪼개기→parked이고, `blocked`는 외부 의존성·재개 조건이 있어야 한다. 커밋·새 acceptance 없이 끝난 태스크의 다음 단위는 agents 안 다른 도구·상위 tier로 승격한다. 단위 상한은 멈춘 세션을 끊는 장치이지 실행의 끝이 아니다. 사용량 한도 실패는 사다리·실패 횟수에 세지 않고 agents 안 다음 후보로 다시 띄운다(분류·clone 공용 차단 기록은 `src/provider-limits.mjs`, 모두 막히면 리셋 대기 또는 `usage-limit` 정지). 태스크 완료 보고는 spec 마감(done 보관·STATE 행 제거·새 lint 오류 없음)으로만 센다 — 어기면(FORMAT 밖 st 포함) 수리 단위 1회→parked. spec lint 오류나 미해결 마감 거절이 있으면 최종 반영하지 않고, 마감이면 실패다(명시적 WIP 원격 인계는 별도).
- `src/agent-catalog.mjs` — `gusta agents`: 설치된 도구(claude·codex)별 로그인·모델·에포트를 모델 호출 없이 모아 조합마다 능력 점수·비용 순서를 매긴다(계열 순위 표 × 에포트, 버전 ID 없음, 못 읽으면 unknown). SETTINGS `agents`(gusta-init, 순서=폴백 순서)가 허용 도구를 정하고, gusta-create-task가 그중 충분한 가장 싼 조합을 태스크 `run:`에 쓴다(lint는 형식만). 태스크 크기 예산은 `src/work-policy.mjs`의 `taskBudget`(`vibe brief --json`의 `size.budget`).
- `src/settings.mjs` — `spec/SETTINGS.md`(패키지 동작 설정)의 키 레지스트리·파서·`vibe settings`. 키·기본값·뜻의 정본은 이 레지스트리이며, 파일이나 키가 없으면 기본값을 쓴다. 잘못된 값은 lint 오류이고, 그 값을 읽는 동작은 추측하지 않고 멈춘다. `src/prune.mjs` — `prune-branches`(기본 true) 정리: CLI가 만든 것 중 합쳐진 단위·묶음 브랜치·worktree·체크포인트 ref·세션 `wip/<tag>`·land에 들어간 세션 worktree와 브랜치(살아 있는 행·실행 중 loop 제외)·기획 브랜치에 올라간 태스크 번호 예약(`refs/gusta/task-ids/*`, `vibe task reserve`)만 지우고, 합쳐지지 않은 커밋·미커밋 변경·진행 중인 일은 `kept`로 보고한다. 실행기는 runner 기록을 놓기 전에 단위만 정리하고, 묶음은 세션 마감의 `vibe prune`이 닫는다(조정자가 아직 묶음을 읽기 때문). 백그라운드 관문(`work finish`)에서는 정리하지 않는다 — 정리 중인 단위가 진행 중으로 보여 `complete` 판정과 경합한다.
- `src/agent-block.mjs` — 대상 프로젝트 `CLAUDE.md`·`AGENTS.md`의 gusta 관리 블록(`<!-- gusta:begin … -->`~`<!-- gusta:end -->`, 탐지는 시작 접두어·끝 줄만). 모델이 아니라 CLI(`gusta agent-block [--check|--remove]`)가 마커 사이만 쓰고 블록 밖은 한 글자도 바꾸지 않는다. SETTINGS `agent-block`(기본 `?` — 대상 프로젝트 소유 문서라 gusta-init이 한 번 묻는다, 맡김은 미정이면 쓰지 않는다)이 true일 때만 쓰고, gusta-update가 갱신하며, `gusta check`가 missing·stale·broken을 잡는다(false·미정이면 통과). broken(짝 없는·중복·역전된 마커, 프로젝트 밖 링크)은 추측해 고치지 않는다. 대상: Claude 설치(lock)는 루트 `CLAUDE.md` → `.claude/CLAUDE.md` → 있는 `AGENTS.md` → 새 `CLAUDE.md` 순, CLAUDE.md가 AGENTS.md 링크이거나 `@AGENTS.md`를 import하면 AGENTS.md만; Codex 설치는 `AGENTS.md`; 같은 파일은 한 번만. **`AGENTS.md`만 있는 프로젝트에 `CLAUDE.md`를 만들지 않는다** — Claude Code는 CLAUDE.md가 없을 때만 AGENTS.md를 읽으므로 기존 지침이 사라진다. 본문은 영어·6줄 이내·에이전트 중립·프로젝트 독립(원칙 13)이고, 경고 문구는 마커 주석에만 둔다(블록 수준 HTML 주석은 Claude Code가 컨텍스트에 싣지 않는다).
- `src/coord-doc.mjs`(순수)·`src/coord-branch.mjs`(저장)·`src/vibe-coord.mjs`(vibe 명령 연결)·`src/vibe-inbox.mjs` — 세션 조정(active·inbox·unlanded·log)은 코드 브랜치의 STATE가 아니라 조정 전용 orphan 브랜치(SETTINGS `coord`, 기본 `gusta`)의 `SESSIONS.md`다. CLI만 plumbing으로 읽고 쓴다(HEAD·index·작업 트리 불변, 비교 갱신이라 같은 clone의 worktree 선점이 원자적). `coord-push`(기본 true)면 사건(선점·해제·inbox·task-done·landed·checkpoint·세션 시작/끝)마다 원격과 합쳐 올리고 같은 태스크는 먼저 올린 쪽이 이긴다(`lost`). push 실패는 작업을 막지 않는다(`unpublished`). 같은 이름의 브랜치가 SESSIONS.md 말고 다른 것을 담고 있으면 읽기·쓰기·publish를 거절한다(덮어쓰지 않음). 이 clone이 처음 쓴 이름은 공유 runtime `coord.json`에 남고 SETTINGS가 다르면 추측하지 않고 멈춘다. 읽기(`vibe status`)는 이관 전 STATE의 옛 active·inbox·log를 합치고 조정 브랜치를 못 써도 죽지 않는다(`coordination.error`); 쓰기는 조정 브랜치에만 한다. Git 없는 대상만 STATE 섹션을 그대로 쓴다. 스킬은 SESSIONS.md를 직접 고치지 않고 `vibe beat|claim|task|inbox|log`로만 기록·조회한다(공통 규칙 2번). 기존 프로젝트는 `gusta migrate`(`sessions-branch`)가 STATE의 세 섹션을 옮긴다 — 옛 CLI 기기는 land의 STATE로 선점해 새 CLI와 서로 보지 못하므로 한 프로젝트의 모든 기기를 함께 올린다.

## 원칙 세부 (CLAUDE.md 원칙 9·11·12)
9. 작업 묶음의 배정·리뷰·통합 단위는 **lane**(lane 없는 태스크는 단독 단위)이다. 단위는 바깥 dep이 모두 통합된 뒤에만 시작하고 안쪽 dep은 같은 worktree에서 순서대로 처리한다 — 서로 기다리는 줄기(단위 그래프 순환)는 lint/board 오류로 기획 단계에서 막는다. 세션·오케스트레이터 에이전트는 모두 같은 `work next` 루프를 돌며 구현·리뷰만 하고, 통합·묶음 검증 같은 기계적 관문은 CLI가 백그라운드 프로세스로 실행한다(모델 턴을 쓰지 않음). 검증은 태스크(변경 영향 검사, `GUSTA_DIFF_BASE`)·단위(integrate 빠른 검사)·공동 통합(살아 있는 참여 세션이 모두 ready인 뒤 고정 후보의 전체 검수 한 번)으로 저장되며, 태스크 단계에 전체 스위트를 다시 넣지 않는다. 묶음의 선택적 taskScope(--tasks)는 배정·board·finish·저장 이력에 일관되게 적용되며 부분 lane과 범위 밖 선행 자동 배정은 금지한다. 그룹 브랜치를 움직이는 통합·sync·finish만 서로 배타적이고, 승인은 겹치지 않는 상위 변경에 유지된다.
   - 묶음 `--push`(원칙 12: 사용자 명시 때만)는 통합 단위를 소유한 작업 브랜치에만 발행한다. land는 살아 있는 참여 세션이 모두 준비된 공동 고정 후보로만 전진하며 작업 브랜치 발행마다 전체 검수를 돌리지 않는다. 미완료 단위는 완료 단위의 작업 브랜치 발행을 막지 않는다. finish는 공동 마감에 준비 상태와 검증 요구를 넘긴다.
   - 살아 있는 세션만 기다린다: 끝난(paused)·90분 신호 없는·head를 못 가져오는 참여자는 그 묶음에서 보류(deferred)될 뿐 철회·반영·선점 이전하지 않는다. 돌아온 세션은 시작·단위 경계마다 land를 merge(rebase 금지)하고, 충돌하면 `land-conflict`로 멈춘다. 다른 기기가 가져간 태스크(lost)는 멈추고 결정함에 남긴다.
   - 단위 verify=빠른 검사, group-verify=조정자 소유 최종 관문(소유권은 원칙 12·`gusta-start/references/verification.md`).
   - 단위 통합·sync의 spec 관문은 모든 오류와 그 단위가 더한 경고만 막는다. 기준에 있던 경고는 `specWarnings`로 알리고 시작 대화가 ready 전 소유 스킬로 정리한다 — 경고를 이유로 남의 단위를 막거나, 남은 경고를 막힘으로만 보고하지 않는다.
   - 같은 트리·같은 명령은 재검증하지 않는다(runtime 검증 캐시). 단위·묶음 검증은 clone 단위 heavy 락으로 하나씩, batch/group은 락 안 캐시 재확인·검증 중 변경 실패, 워커/리뷰어는 기본 거절. 검증 SHA를 받는 push는 sync로 달라진 코드를 거절한다. 재제출은 고친 커밋부터의 diff만 태스크 단계에 넘긴다. 최종 관문의 실측 시간은 runtime `timings.json`에 남아 시간 한도 맡김의 마감 예약이 된다.
   - 리뷰는 위험한 단위만(기본 `--review risky`, 기준은 coordinator.md). gusta-self-improve-remote 묶음은 `--review all`(자율 개선은 위험도와 무관하게 독립 검토 필수).
   - explore 태스크와 그 후속은 묶음에 배정하지 않는다(`main-session`) — 메인 세션에서 시간 제한과 exit로 끝낸다.
   - 워커는 SSOT를 쓰지 않는다. 맡김에서는 워커의 결정 요청 → 조정자 잠정 gusta-update-ssot → `--note` 재개 시 실행기가 기획 브랜치를 합치고 **같은 세션**을 resume한다.
11. 맡김(autopilot)에는 사람 입력을 기다리는 경로가 없다. gusta-start는 시작 때 묻지 않는다 — 실행 정보(대상 태스크·순서·검증·반영 설정·다른 세션과 기기의 진행 — `vibe status`의 `others`·`held`·`unlanded`, 아직 push 안 된 것 포함)를 보여 주고 바로 시작한다. 질문은 preflight 실패 1회뿐이고, 그 뒤 결정 지점은 추천안 채택 + inbox `decided`(`vibe inbox add`) + 보고서다(기획 스킬도 받았어야 할 질문을 결정함에 남긴다). 사람에게 묻는 일은 실행 전에 gusta-plan·gusta-sketch에서 끝낸다(`/gusta-start <요청>`은 요청문을 사람의 결정으로 보고 공백만 추천안으로 채운다).
   - 과금·데이터 삭제·개인정보·보안 정책은 `[?]`로 두고, 되돌리기 어렵거나 프로젝트 밖에 영향을 주는 일과 함께 주차한다. SSOT에는 잠정 결정도 일반 `[o]`로만 들어간다(잠정 표시는 inbox가 ID로 가리킨다, 원칙 5).
   - 권한 확인 창도 질문이다 — 사람이 없으면 세션이 멈추고 캐시가 식는다. 창이 뜰 만한 호출(프로젝트 밖 쓰기·삭제, `cd`가 섞인 복합 명령, `rm -rf`·`kill`·`curl`·`sudo`, 부하 에이전트)은 하지 않고 주차한다(공통 규칙 4번 + gusta-start 3절). CLI가 맡김에 돌려주는 지시문(`src/work-wait.mjs` UNATTENDED)도 이 목록을 어기지 않는다. 세션 기록도 파일 편집·커밋 없이 `vibe inbox add`·`vibe log` 한 번 호출로 쓴다(복합 명령 금지, 따옴표·`|`가 섞인 본문은 `--file`). CLI가 띄우는 헤드리스 작성 세션(loop 단위·work run 워커·ab 변형·preflight probe)의 권한은 SETTINGS `permission-mode`(기본 bypass)다 — 답할 사람이 없는 세션에 권한 창·sandbox 거절을 두지 않는다. 그 세션의 도구·모델·에포트는 실행 중인 모델이 아니라 CLI가 태스크 `run:`과 SETTINGS `agents`로 정한다(`src/agent-route.mjs`, agents 미정이면 `needs-init`으로 시작하지 않음). 리뷰어는 항상 읽기 전용이다. 헤드리스 Claude 세션은 SETTINGS `headless-mcp`(기본 isolate: `--strict-mcp-config`만, `--mcp-config` 없음)로 MCP 서버를 싣지 않는다 — 권한 창 없이 도는 세션이 프로젝트 밖 서비스를 바꾸지 않게, 워커가 커밋한 `.mcp.json`이 승인 없이 리뷰어·다음 단위에서 돌지 않게. MCP가 필요한 프로젝트는 `inherit`.
   - 디자인 모드는 맡김에 없다: 그 checkout에서 열려 있으면 preflight 실패·loop 정지·`vibe push` 거절(다른 worktree 무관), 맡김은 디자인 변경을 주차한다. `vibe design verify`는 미커밋 트리의 task 검사만 실행하고 batch·CI는 보류한다(`finalVerified:false`). 디자인 종료·하위 브랜치 커밋 뒤 공동 통합에 제출하며, 전체 검수는 원칙 9의 고정 후보에서만 한다.
   - gusta-self-improve-remote의 위임 범위·예산·발행 권한은 ARCH 결정에 두고 맡김 실행과 구별한다. 큰 변화는 제안 후 사람 판단까지 주차하고 기본 종료점은 PR(자동 merge는 별도 위임). 세션 밖 실행은 실제 스케줄러 연결이 필요하며 내장 vibe loop의 no-work 종료는 유지한다.
12. 태스크마다 커밋한다. 반영은 SETTINGS land·land-via·push가 정하고 기본은 push하지 않는다(`push: false`) — push마다 원격 CI가 돌아 빌드 시간을 쓴다. 세션 끝·loop 멈춤에는 ready로 제출하고 살아 있는 참여 세션이 모두 준비된 고정 후보를 한 소유자가 검수·반영한다(묶음 경계는 보고서만, land 미정이면 커밋만). 조정 브랜치만 예외다: `coord-push`(기본 true)면 `push`와 무관하게 사건마다 CLI가 올린다(모델 턴 없음, 실패해도 작업을 막지 않음) — 코드와 히스토리를 공유하지 않는 별도 브랜치라 코드 CI를 돌리지 않고, 그래야 다른 기기에서 아직 push 안 된 진행이 보인다(브랜치마다 도는 미리보기 배포·웹훅을 거르는 일은 대상 프로젝트 몫). `vibe status`의 `concurrency: strict`(살아 있는 다른 세션이 보임)는 표시일 뿐 동작을 바꾸지 않는다 — 선점은 그와 무관하게 늘 조정 브랜치로 하고(아래), 단위별 코드 push/e2e를 자동으로 켜지 않는다. 묶음 `--push`는 사용자 명시 시 소유 작업 브랜치만 발행한다. loop `--push-each-unit`는 의도를 기록하되 단위 중 발행을 유예하고 공동 마감으로 모은다. 설정 적용을 발행 성공으로 보고하지 않으며, 두 옵션 모두 land의 단위별 반영·전체 검수를 허용하지 않는다. 장기 맡김은 `vibe loop`로 단위마다 새 세션을 만들고 CI/긴 명령 대기는 CLI가 처리한다. 1시간 넘는 작업은 `vibe checkpoint`로 `wip/<tag>`에 스냅샷한다(push 브랜치를 WIP로 더럽히지 않는다). 배포는 사용자가 요청할 때 `vibe deploy`만 한다. 선점은 push 대상·깨끗한 트리 없이 항상 조정 브랜치의 active 행으로 한다: 같은 clone의 worktree는 원자적이고, 다른 기기와는 조정 브랜치를 먼저 올린 쪽이 이긴다(진 쪽은 `lost`). 끝났지만 land에 안 들어간 태스크는 `unlanded`가 다시 집히지 않게 막는다. STATE는 `vibe merge-state` 드라이버로 섹션 단위 병합한다(사용자 git 설정에 쓰지 않고 호출마다 `-c`로) — SESSIONS는 멈추지 않고 합친다(줄은 합집합, 행은 나중 `at`, 겹친 선점은 원격).
   기획 문서는 예외: SETTINGS `plan` 브랜치(미정이면 land, 그것도 아니면 저장소 기본 브랜치)가 채번·기획의 정본이다. 어느 checkout·worktree에서든 `vibe plan-sync` 후 기획하고, spec/만 담은 기획 커밋을 `vibe plan-push`로 그 브랜치에 바로 올린다(push 설정과 무관, 코드는 실리지 않음, 원격에 브랜치가 없으면 깨끗한 로컬 브랜치만 fast-forward). 같은 T###는 먼저 올린 쪽이 이기고 진 쪽이 다시 채번한다. 올린 결과를 merge로 되가져와 이후 3-way 병합(태스크 아카이브·STATE 행 제거)이 todo를 되살리지 않게 한다. spec만 바뀐 push에서 CI·빌드를 건너뛰는 설정은 대상 프로젝트 몫이다.

## 검증 세부
- 스킬 수정은 영향 계약·구조 검사로 확인한다. `npm run check`(전체 테스트 + 스킬 구조 + 패키징)는 공유 마감의 고정 통합 후보에서 한 번 실행하고, 실패·변경 범위만 재검사한다.
- `node --test`는 파일끼리만 병렬이다 — 느린 테스트는 파일을 나눈다(작업 묶음은 `test/work-groups*.test.mjs`, 30태스크 scale 파일이 스위트 하한).
- loop 종료/설정 회귀는 `test/vibe-loop-control.test.mjs`: 가짜 단위·격리 bare Git·실제 호스트 강제 종료·실제 알림 자식 명령. 모델 호출과 운영 브랜치 push 없이 전체 단위 경계를 검증한다.
- 로컬 설치 테스트: `node ./bin/gusta.mjs install --target <경로>` 후 `check --target <경로>`.
- `lint --target <경로>` — 타겟 spec/의 FORMAT 불변식 검사(규칙은 `src/spec-lint.mjs`). `--hints`로 검토 후보 전체(기본 10건).
- `vibe brief <T###|ID-n|ID|ID@rev>` — 태스크·결정 브리핑(마크다운, `--json`·`--ref`·`--deep`). 대표 태스크 전달량은 `node scripts/measure-brief.mjs --target <경로> [--tokens]`(읽기 전용).
- `vibe` 하위 명령(`vibe --help`) — gusta-start·gusta-design-mode의 세션 도구. 테스트는 bare 원격과 clone 둘로 다른 기기를 재현한다(`test/vibe.test.mjs`, 조정 브랜치는 `test/coord-doc.test.mjs`(순수)·`test/coord-branch.test.mjs`·`test/vibe-coord.test.mjs`), 맡김 실행기는 가짜 provider로(`test/work-autopilot.test.mjs`).

## 배포 세부
- 릴리스는 `npm version patch` 후 main에 푸시한다. release.yml은 같은 저장소 main push의 성공한 CI와 정확히 같은 SHA만 받아 검증을 재사용하고, 버전이 npm에 없을 때만 provenance·발행 도구 검사 뒤 publish한다. 전체 release:check는 중복 실행하지 않는다.
- npm 인증은 Trusted Publishing(OIDC) — 토큰 시크릿 없음. npmjs.com 패키지 설정에 GitHub Actions(hetarho/gusta, release.yml)가 등록돼 있어야 한다.
- 배포 전용 npm은 11.21.2로 고정한다. npm/cli#10078의 임시 대응으로 `scripts/prepare-publish.mjs`가 해당 CLI의 bundled sigstore 4.1.1에서 기존 Rekor 항목 조회만 켠다. 예상 버전·구조가 다르면 실패하며, 실제 도구의 409 복구·증거 보존·다른 오류 거절을 배포 전에 검사한다. 서명/provenance는 유지하며 npm에서 복구를 기본 제공하면 이 임시 수정을 제거한다. 소비자 의존성·설치에는 적용하지 않는다.
