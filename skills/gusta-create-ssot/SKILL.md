# gusta-create-ssot — 기획자 인터뷰 → 도메인 SSOT

**역할: 기획자.** 이 스킬 안에서 너는 기술을 이해하는 기획자다. 무엇을·왜·어디까지 만들지 결정한다.
어떻게 만들지(스키마·라이브러리·API 형태)는 묻지도 정하지도 않는다 — 필요해 보이면 "gusta-create-task에서
엔지니어가 결정할 것"으로 넘긴다. 반대로 기획 공백을 기술 디폴트로 얼버무리지도 않는다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 `vibe status --json`(실행기 안에서는 brief)으로 필요한 요약만 본다. spec/이 없으면 /gusta-plan을 안내하고 멈춘다. `settings.unset`이 있으면 gusta-init으로 정한다(맡김에서는 묻지 않고 미정인 채 진행한다).
2. **문서 먼저**: 쓰기·구현 전에 문서 상태는 STATE에, 세션 기록은 `vibe beat|claim|inbox|log`로만 남긴다(SESSIONS.md를 직접 고치지 않는다). 구현은 land·deploy·plan 브랜치가 아닌 하위 브랜치의 배정된 작업 공간에서 한다. `vibe status`에 `design`이 있으면 커밋·push 전에 디자인이 끝났는지 묻고, 끝났으면 gusta-design-mode 마감부터 한다.
3. 산출 문서는 FORMAT 표기만 쓴다 — `vibe format --section <절>`로 필요한 절만 본다.
4. 질문·보고는 cfg.lang·cfg.level대로, 산출 문서 언어는 FORMAT 언어 규칙대로. 선택지형 질문 도구가 있으면 쓴다. 맡김(gusta-start·loop 단위)에서는 묻지 않는다 — 추천안으로 진행해 `vibe inbox add`로 남기고, 되돌리기 어렵거나 프로젝트 밖에 영향을 주는 일과 권한 창이 뜰 만한 명령은 주차한다. 사용자가 직접 부른 스킬은 묻는다.
5. **읽기**: `vibe brief <ID> --summary`로 범위를 찾고 필요한 블록만 원문째 읽는다 — 출력의 complete·`next`가 덜 읽은 곳을 알려 준다. STATE·FORMAT·ARCH·큰 코드·tasks/done/을 통째로 읽지 않는다. 긴 출력은 요약·tail만 보고 전체는 파일로 남긴다.

어느 checkout에서든 기획 쓰기·채번 전 `vibe plan-sync`, spec/만 담은 기획 커밋 직후 `vibe plan-push`(정본·거절 시 재채번은 `vibe format --section settings`의 `plan`).

## 1. 시작
STATE 읽기 → `vibe log --text 'gusta-create-ssot <topic> start'` → STATE ssot 표(도메인 목록)와 `rg <키워드> spec/ssot`로 중복·연관 확인(ssot/ 전체를 읽지 않는다).
같은 도메인이 이미 있으면 gusta-update-ssot로 전환을 제안한다.
gusta-plan에서 정한 해석표나 gusta-sketch에서 고른 시안의 결정(채택·안 할 것·v1 경계)이 재료다 — 2단계 인터뷰는 거기서 정하지 못한 공백과 [?]만 채운다. plan·sketch가 미뤄 둔 spec/ideation/ 문서(open·ready)를 재료로 쓰면 domains의 다음 미반영 채택 줄과 vision·shape·explored를 읽고 문서·STATE st를 ready로 바꾼다. ideation/done/은 기본 입력이 아니다. 같은 도메인이 이미 있으면 원본 경로·반영할 범위를 gusta-update-ssot로 함께 넘긴다.
gusta-start 요청 실행이면 요청문이 재료다 — 요청문이 정한 것은 사용자 결정으로 그대로 쓰고, 정하지 않은 공백만 맡김 규칙으로 채운다.

## 2. 기획 인터뷰
아래를 전부 결정으로 만들 수 있을 때까지 묻는다. 한 번에 2~4개씩. 이미 문서·대화에 답이 있으면 묻지 않는다.
- **문제/목적** — 왜 필요한가, 성공하면 무엇이 달라지나
- **타겟** — 누가 쓰나
- **범위** — 포함 / **명시적 제외** (제외 목록이 스코프 크리프를 막는다)
- **핵심 플로우** — 사용자가 겪는 순서 (FORMAT 플로우 표기)
- **정책** — 권한, 요금·한도, 데이터 보존·삭제, 실패 시 사용자 경험
- **우선순위** — 지금 vs 나중 (나중은 [x] 보류로 기록)

level별 질문법:
- **expert**: 정책 엣지(동시성, 악용, 한도 초과 시 UX)까지 직접 묻는다. 선택지는 용어 나열로 짧게.
- **mid**: 핵심 갈림길만 선택지 + 영향 1줄. 엣지는 추천안을 제시하고 확인.
- **novice**: 기획 결정을 AI가 대신 정하지 않는다 — 기술과 달리 기획은 novice일수록 오히려 더 촘촘히 묻는다. 다만 용어 없이 "이런 상황이 생기면 어떻게 되면 좋겠어요?" 식 시나리오로 풀고, 질문마다 추천안을 붙여 고르기 쉽게 한다. 사용자가 "알아서 해줘"라고 넘긴 항목도 과금·데이터 삭제·개인정보만큼은 반드시 명시적으로 확인받는다.
- **맡김(gusta-start 실행)**: 위 질문을 똑같이 만들되 묻지 않고 추천안으로 결정을 쓴다. 질문마다 inbox `decided` 한 줄(`<question> → <choice> (alt: …)`)을 남겨 사용자가 나중에 같은 질문을 검토하게 한다. 과금·데이터 삭제·개인정보·보안은 정하지 않고 `[?]`로 두고 inbox `parked`.

## 3. 작성
도메인 ID 확정(기존과 충돌 금지) → 이 스킬 폴더의 assets/ssot.md를 `spec/ssot/<ID>.md`로 복사해 채운다. (opt) 섹션(flow·constraints)은 안 쓰면 삭제, `<...>` 자리표시는 전부 실제 내용으로 교체.
품질 기준: **의사결정 요소(결정·근거·제약·미정)는 전부, 문장은 최소.** 배경 서사 금지. 못 정한 것은 [?]로 남긴다.
**기존 문서 이관**: 재료가 기존 문서(PRD·구 스펙·README·다른 저장소의 문서)면 붙여넣지 않는다. 한 문단씩 "지금 지켜야 하는 규칙인가"로 걸러 결정 라인으로 다시 쓰고, 아래 최종 점검을 똑같이 통과시킨다 — 이관 때 길게 들어온 문서는 계속 길다. 원문에 있으나 지금도 유효한지 모르는 항목은 추측으로 옮기지 말고 [?]로 등록한다.

**최종 점검** — 확인 요청 전에 한 줄씩 통과시킨다. SSOT에는 지금 지켜야 하는 규칙만 남는다. 요청·대화의 흔적은 태스크 파일(1회용)에는 있어도 되지만 SSOT에는 절대 남기지 않는다.
- 한 결정이 독립적으로 이해·검증되는 정책 단위인가 — 따로 바뀔 수 있는 정책이 섞였으면 쪼갠다. 신호: ` ← ` 두 개 이상, ` · ` 세 덩어리 이상, 한 줄 700자 초과.
- 조건이 많으면 줄을 합치지 말고 결정 블록(2칸 들여쓴 하위 항목·표)으로 편다 — 줄바꿈을 없애는 것은 간결화가 아니다.
- 남겨야 할 것이 다 남았는가 — 호환성, 실패 조건, 보안·과금·데이터 보존, 수치와 단위, 부정 표현(no·never·only), 트레이드오프의 ← 이유.
- 빼야 할 것이 없는가 — 요청 경위("user asked / as discussed"), 승인자·날짜, 인터뷰 순서, 과거 화면·과거 버그 해명, 폐기된 방식의 상세, 미사여구. 날짜는 측정 출처(`measured YYMMDD`)일 때만 남는다.
- 범위를 정하는 제외는 [o] 부정형 한 줄이고, [x]는 더 이상 유효하지 않은 결정뿐인가 — [x]는 왜 논의됐는지 설명하지 않는다.
- 코드나 다른 SSOT가 정본인 상세를 옮겨 적지 않았는가 — 참조(→<ID>-n, 경로)로 대체. 새로 쓰는 참조에는 종류를 붙인다: 그것 없이 이 규칙을 적용할 수 없으면 `→!`, 규칙 자체가 거기 있으면 `→=`, 배경이면 `→~`. 프로젝트 FORMAT에 이 표기가 없으면(옛 FORMAT) `→`만 쓰고 next에 FORMAT 이관을 남긴다.
- 섹션이 FORMAT 골격(decisions·flow·constraints·chg)뿐인가 — discussion·notes·context·background 같은 섹션은 금지. 내용이 결정이면 decisions로 흡수, 아니면 삭제.
- chg는 `- rN YYMMDD 요약` 한 줄씩인가 — 변경 경위 서술 금지, ✎는 old→new만.
- `<...>` 자리표시·빈 (opt) 섹션이 없는가.

초안을 사용자에게 확인받는다 — novice: 풀어서 설명 + 원문 / mid: 원문 + 핵심 결정 요약 / expert: 원문만.

## 4. 마감
STATE: ssot 행 추가 `<ID> | 1 | 0 | all | <[?] 수>` / next에 `gusta-create-task <ID>`. `vibe log` 1줄.
ideation 문서에서 시작했다면 [전환 마감 절차](references/ideation.md)를 수행한다.
