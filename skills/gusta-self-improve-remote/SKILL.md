# gusta-self-improve-remote — 지속 개선 조정자

**역할: 개선 조정자.** 지시 없이 실행 기록·코드·작업 흐름에서 개선 후보를 찾아 문제 발견 → 고정 지표의 반복 실험 → 최선 후보 → 독립 검토 → PR → 결과 관찰을 운영한다. 태스크·구현·기획은 기존 스킬에 맡긴다. 위임 범위·예산·발행 권한은 ARCH 결정에서 온다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 `vibe status --json`(실행기 안에서는 brief)으로 필요한 요약만 본다. spec/이 없으면 /gusta-plan을 안내하고 멈춘다. `settings.unset`이 있으면 gusta-init으로 정한다(맡김에서는 묻지 않고 미정인 채 진행한다).
2. **문서 먼저**: 쓰기·구현 전에 문서 상태는 STATE에, 세션 기록은 `vibe beat|claim|inbox|log`로만 남긴다(SESSIONS.md를 직접 고치지 않는다). 구현은 land·deploy·plan 브랜치가 아닌 하위 브랜치의 배정된 작업 공간에서 한다. `vibe status`에 `design`이 있으면 커밋·push 전에 디자인이 끝났는지 묻고, 끝났으면 gusta-design-mode 마감부터 한다.
3. 산출 문서는 FORMAT 표기만 쓴다 — `vibe format --section <절>`로 필요한 절만 본다.
4. 질문·보고는 cfg.lang·cfg.level대로, 산출 문서 언어는 FORMAT 언어 규칙대로. 선택지형 질문 도구가 있으면 쓴다. 맡김(gusta-start·loop 단위)에서는 묻지 않는다 — 추천안으로 진행해 `vibe inbox add`로 남기고, 되돌리기 어렵거나 프로젝트 밖에 영향을 주는 일과 권한 창이 뜰 만한 명령은 주차한다. 사용자가 직접 부른 스킬은 묻는다.
5. **읽기**: `vibe brief <ID> --summary`로 범위를 찾고 필요한 블록만 원문째 읽는다 — 출력의 complete·`next`가 덜 읽은 곳을 알려 준다. STATE·FORMAT·ARCH·큰 코드·tasks/done/을 통째로 읽지 않는다. 긴 출력은 요약·tail만 보고 전체는 파일로 남긴다.

## 1. 활성화·재개
SETTINGS `usage-measurement`가 true인 시작 대화는 [사용량 절차](../gusta-start/references/usage.md)로 작업 전 기준선을 시작한다. 최상위 대화는 마감(할 일 없음·실패·주차 포함)에 Markdown 파일을 저장하고 최종 **채팅**에 summary·reportFile 링크를 전달한다(JSON artifact만으로 끝내지 않음, false면 실행하지 않음).

처음 설정하거나 실행기를 연결할 때 [운영 정책](references/operation.md)을 읽는다. 위임된 범위에서는 후보마다 승인을 다시 묻지 않고, 정책이 없으면 이번 요청 범위의 진단·검토 가능한 초안까지만 한다.

- 정책·최근 개선 보고서·열린 개선 PR·진행 중 작업의 소유권부터 확인한다. 명시적인 사용자 작업, 실패한 필수 CI, 진행 중 디자인이 우선이고, 이미 도는 사이클이 있으면 합류하거나 끝낸다.
- 기본은 24시간에 문제 하나를 골라 그 고정 지표를 예산 안에서 여러 가설로 개선한다. 새 세션도 최초 기준선·최선 후보·시도 기록·사용 예산·실패 횟수·열린 PR을 이어받는다.

## 2. 지시 없이 문제 발견
전체 저장소를 매번 감사하지 않는다 — 지난 관찰 이후의 변경과 비용 상위 지점부터 보고, 근거 없는 영역은 다음 사이클로 넘긴다. 조정자는 코드·로그를 직접 훑지 않고 영역을 나눠 [탐색 프롬프트](../gusta-self-improve/assets/scout-prompt.md)로 하위 세션(네이티브 또는 `work scout`)에 맡긴 뒤, 제안과 그것이 가리킨 근거만 확인한다. 정확성·검증 공백은 속도보다 먼저다. 영역: 실행 비용(CI·테스트·벤치마크의 실제 시간 — `vibe loop` 보고서의 `- time:` 줄·loop.json `time` 포함), 테스트(중복·영향보다 넓은 실행, 태스크 단계 전체 스위트, 비싼 fixture, flaky — 코드 결합으로 느리면 경계 주입 구조 개선), 엔진·코드(반복 계산·할당·I/O, 자주 깨지는 경계, 프로파일 병목), 업무 흐름(반복 검증·읽기·기획, 재작업·인계 누락, 선점 충돌, 피드백 지연).

`spec/review/<slug>.md` 골격을 쓴다. finding은 위치·문제·영향, notes는 관측 출처·기준 commit·측정 시각·가설·기대 이익·비용·반증 조건. 원인·경로·불변식이 같은 기존 finding/태스크/PR이 있으면 이어간다. 기각·실패한 후보는 새 근거가 있을 때만 다시 연다. 가치 있는 후보가 없으면 관찰 범위와 다음 시점을 기록하고 끝낸다.

## 3. 채택과 사람 판단 경계
- **위임 범위의 작은 개선**(결과·계약·검증 범위 보존, 영향·되돌림 국소적): 사전 위임을 근거로 [o] 채택, notes·inbox decided에 정책 결정 참조와 이유 → gusta-create-task → gusta-implement-task → 독립 검토 → PR.
- **큰 변화·근거 부족**(알고리즘 의미·확률 분포·정밀도·공개 API·저장 포맷 변경, 검증 범위 축소, 광범위 구조/의존성 변경, 영향 불명): [?] 유지, 설계·측정·호환성·되돌림을 갖춘 제안/격리된 초안까지만 — 사람 판단 전 적용·통합하지 않는다.
- **위임 밖**(예산 초과, 과금·데이터 삭제·개인정보·보안 정책, 배포·외부 시스템 변경): 그 작업만 parked, 다른 허용 후보 또는 마감.

파일·줄 수는 보조 신호다 — 한 줄이어도 결과 의미를 바꾸면 큰 변화다. 큰 변화를 작은 PR 여러 개로 나눠 사람 판단을 피하지 않는다. 사람 판단 요청은 막연한 허가가 아니라 [PR 본문 템플릿](assets/pr-body.md)대로 후보·증거·대안·권장 판단을 갖춘다.

## 4. 측정과 구현
반복 실험은 [실험 루프](references/experiments.md), 비용 측정은 [측정 절차](references/measurement.md)를 읽는다. 기존 필수 검사를 없애거나 임계값·샘플·정확도를 낮춰 빨라졌다고 하지 않는다.
- gusta-create-task는 채택 finding을 리뷰 태스크로 만든다. 불확실한 프로파일·시뮬레이션 탐색은 wall-clock 제한과 exit가 있는 explore 태스크로 분리해 메인 세션에서 하고, 후속 구현은 실험 결과로 범위가 정해진 뒤 만든다.
- 기획·구현 전에 `vibe session open --kind self-improve-remote --tag <tag> --json`으로 전용 worktree·세션 브랜치를 확보하고 반환 targetRoot만 쓴다.
- 코드·테스트·워크플로 수정은 조정자가 직접 하지 않는다 — 하위 세션(작업 묶음 `work run --review all` 또는 네이티브)이 gusta-implement-task로 하고, 검사 단계는 [공유 검증 계약](../gusta-start/references/verification.md)을 따른다.
- 예산 부족·무진행·기준 미달이면 측정과 진행분을 보존하고 끝낸다. 미완료 검증을 pass로 기록하거나 자동 채택하지 않는다.

## 5. 독립 검토·PR
구현 전에 검토자와 발행 경로를 확인하고, 제출할 때 [검토·발행 절차](references/review.md)를 읽는다. **모든 자율 개선은 작성자와 다른 새 세션의 검토가 필요하다**(같은 LLM의 별도 세션도 된다). 역할 이름만 바꿔 자기 PR을 승인하지 않는다. 검토자·권한이 없으면 검토 패킷을 남기고 review pending으로 끝낸다.

개선 브랜치 push·PR은 사전 위임 범위에서 한다. PR 대상(base)은 SETTINGS land이고, land가 미정이면 PR 없이 parked에 남긴다. `vibe push`나 plan 브랜치로 land에 직행하지 않는다. 기본 종료점은 독립 검토와 필수 관문을 통과한 PR이다 — merge는 별도의 명시적 사전 위임이 있을 때만 한다.

## 6. 피드백·종료
[보고서 골격](../gusta-start/assets/report.md)만 쓴다(새 cfg 키·STATE 섹션 없음): done=finding/태스크·commit·PR, decided=위임 내 채택 이유, parked=사람 판단/검토/권한 부족, checks=전후 수치·원시 근거·검증/미실행·소모 예산, next=다음 관찰 시각·재개 지점.

merge된 개선은 다음 사이클에 실제 CI/실행 기록으로 효과와 회귀를 확인한다(merge 전 국소 벤치마크는 성과로 세지 않는다). 회귀면 새 최적화보다 중단·되돌림 제안이 먼저다. 폐기·실패 실험과 비용도 남겨 같은 시도를 반복하지 않는다. 원인이 확인된 반복 교정은 작은 검사·실행 규칙으로 옮기고, 판단이 필요한 교훈만 스킬 문장으로 남긴다.

최종 보고: expert는 수치·근거·commit·PR·판정, mid는 변화와 비용/한계, novice는 달라질 작업 경험과 사람이 결정할 사항부터. 실행기 연결 여부와 다음 실행 조건을 숨기지 않는다.
