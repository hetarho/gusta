# 요청 실행 — `/gusta-start <요청>`

SKILL.md 1절에서 인자가 규칙·동작을 바꾸는 요청일 때 시작 대화가 읽고, 3절은 그 요청을 기획하는 첫 loop 단위가 따른다. 요청을 기획 한 조각(SSOT·태스크)으로 옮기고 그 태스크를 같은 맡김으로 끝까지 구현한다. 묻지 않는다.

## 1. 판별
- 요청 실행: 규칙·동작·화면·데이터 계약을 새로 만들거나 바꾸는 요청("<동작>을 이렇게 바꿔줘", "<기능> 추가해줘"). 같이 준 태스크 ID·시간 한도도 적용한다.
- 아니다: 경량 경로 조건을 모두 만족하는 작은 수정(2절 경량 경로), inbox 정리·이어가기 보존(2절 표).
- spec/이 없거나 ARCH에 검증 명령이 없으면 실행하지 않고 "/gusta-plan으로 아키텍처부터 정하세요"로 끝낸다 — 스택·구조는 사람이 고른다. route design이면 1절 안내로 끝내고, repair면 복구부터 한다.

## 2. 보여 주고 맡기기
1절 실행 정보에 요청 해석을 더해 한 번 보여 주고 기다리지 않는다: 바꿀 도메인·결정(새 도메인이면 그 이름), 요청문이 정하지 않아 추천안으로 채울 공백, 주차할 민감 정책, 이번 범위 밖의 실행 가능한 기존 태스크 수(실행하지 않는다). 해석은 `vibe status`·`vibe brief --summary` 수준에서 끝내고, 기획 스킬·코드는 이 대화에서 읽지 않는다(그 읽기는 기획 단위와 함께 사라진다). 사용자가 끼어들어 고치면 그 말을 요청에 합친다.
요청 원문과 해석·공백 목록을 세션 임시 폴더의 파일에 쓰고 `vibe loop --tag <tag> --request-file <path> --json`으로 시작한다. 첫 단위가 3절을 하고, 이어서 그 단위가 만든 태스크와 그 dep만 실행한다(`--tasks`와 함께 쓰지 않는다). 태스크 목록은 `request-planned` 이벤트·보고서로 받아 진행 보고에 알린다. 작업 묶음 조건이면 `--max-units 1`로 기획 단위만 돌린 뒤 만든 태스크로 [조정자 절차](coordinator.md)를 시작한다.

## 3. 기획 한 조각 (기획 단위)
- `vibe plan-sync` 후 기존 도메인은 gusta-update-ssot, 새 도메인은 gusta-create-ssot, 이어서 gusta-create-task를 한다. 구현은 하지 않는다.
- 요청문이 직접 정한 것은 사용자 결정이다 — 그대로 SSOT에 쓰고 inbox에 남기지 않는다. 기존 결정과 다르면 요청대로 개정한다. 요청문이 정하지 않은 공백만 기획 스킬의 맡김 규칙(추천안+inbox `decided`)으로 채운다. 화면처럼 갈리는 선택도 추천안 하나로 가고 대안을 decided에 남긴다(바꾸려면 /gusta-sketch).
- 과금·데이터 삭제·개인정보·보안 정책은 요청문이 명시한 것만 반영한다. 정하지 않은 공백은 `[?]`로 두고 그 공백에 걸린 태스크만 parked로 남긴다. 요청이 직접 요구하지 않은 큰 변화(결과 의미·공개 계약·검증 범위)는 적용하지 않고 parked로 제안한다.
- spec/만 담은 기획 커밋 직후 `vibe plan-push`. ID 충돌로 거절되면 기획 스킬이 다시 채번해 올린다. 그 밖의 실패는 parked로 남기고 구현하지 않는다.

## 4. 구현과 마감
- 범위 = 이 요청으로 만든 태스크 + 그 태스크가 dep으로 기다리는 미완료 태스크(loop가 기획 단위 뒤 정한다). 다른 기존 태스크는 하지 않는다.
- 실행은 일반 맡김과 같다: 커밋·검증·반영은 SKILL.md 4절, 마감은 5절. 관문은 마지막 한 번이다([최종 검증](verification.md)).
- 보고서 done에 바뀐 SSOT rev·구현한 태스크를, decided에 채운 공백을 남긴다. 끝 보고: 요청 → 바뀐 결정(ID@rev) → 태스크·커밋 → 검증·반영 → 결정함 수(바꾸려면 /gusta-plan).
