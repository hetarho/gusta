# gusta-doc-review — SSOT 편집 (의미 보존)

**역할: 편집자.** 같은 규칙이 더 잘 읽히게 만드는 데까지가 권한이다 — 규칙이 바뀌면 gusta-update-ssot 몫이다. 목표는 짧게가 아니라 한 결정을 독립적으로 이해·검증할 수 있게 하는 것이다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 `vibe status --json`(실행기 안에서는 brief)으로 필요한 요약만 본다. spec/이 없으면 /gusta-plan을 안내하고 멈춘다. `settings.unset`이 있으면 gusta-init으로 정한다(맡김에서는 묻지 않고 미정인 채 진행한다).
2. **문서 먼저**: 쓰기·구현 전에 문서 상태는 STATE에, 세션 기록은 `vibe beat|claim|inbox|log`로만 남긴다(SESSIONS.md를 직접 고치지 않는다). 구현은 land·deploy·plan 브랜치가 아닌 하위 브랜치의 배정된 작업 공간에서 한다. `vibe status`에 `design`이 있으면 커밋·push 전에 디자인이 끝났는지 묻고, 끝났으면 gusta-design-mode 마감부터 한다.
3. 산출 문서는 FORMAT 표기만 쓴다 — `vibe format --section <절>`로 필요한 절만 본다.
4. 질문·보고는 cfg.lang·cfg.level대로, 산출 문서 언어는 FORMAT 언어 규칙대로. 선택지형 질문 도구가 있으면 쓴다. 맡김(gusta-start·loop 단위)에서는 묻지 않는다 — 추천안으로 진행해 `vibe inbox add`로 남기고, 되돌리기 어렵거나 프로젝트 밖에 영향을 주는 일과 권한 창이 뜰 만한 명령은 주차한다. 사용자가 직접 부른 스킬은 묻는다.
5. **읽기**: `vibe brief <ID> --summary`로 범위를 찾고 필요한 블록만 원문째 읽는다 — 출력의 complete·`next`가 덜 읽은 곳을 알려 준다. STATE·FORMAT·ARCH·큰 코드·tasks/done/을 통째로 읽지 않는다. 긴 출력은 요약·tail만 보고 전체는 파일로 남긴다.

기획 쓰기·채번 전 `vibe plan-sync`, spec/만 담은 기획 커밋 직후 `vibe plan-push`.

## 1. 시작
- 대상: 사용자가 지정한 도메인, 없으면 STATE ssot 표의 rev와 `wc -c spec/ssot/*.md` 순으로 **한 세션에 끝낼 만큼만**(나머지는 next). 편집 대상은 `spec/ssot/*.md`(ARCH 포함)뿐이고 STATE는 next만 갱신한다. 고른 문서는 편집 전에 `## chg`까지 전부 읽는다.
- 기본은 편집까지 한다. "검토만/제안만"이면 파일을 건드리지 않는다. `vibe log --text 'gusta-doc-review <IDs> start'`.
- `npx @haeram/gusta lint`(실행기면 cliCommand)의 검토 후보는 출발점일 뿐이다 — 후보가 아니어도 2절 신호면 대상이고, 후보라도 자동으로 고치지 않는다.
- 진행 중 태스크(STATE doing, 묶음이면 공유 보드의 활성 attempt)가 참조하는 도메인은 분할하지 않고 문구만 정리한다(분할 제안은 보고에).

## 2. 신호 → 편집 (결정 하나씩, 의미를 보존하는 것만)
- **복합 결정**(` ← ` 둘 이상, ` · ` 세 덩어리 이상, 한 줄 700자 초과, "그리고 또" 나열) → 결정 블록(FORMAT)으로 펴 조건·예외·열거값을 2칸 들여쓴 하위 항목이나 표로 내린다. 독립적으로 바뀔 정책은 분할한다: 원래 번호는 머리 정책이 갖고, 떨어진 정책만 새 번호(현재 최대+1). 번호 재사용·재번호 금지.
- **과거 흔적**(요청 경위·승인자·날짜 `owner decision 2026-09-05`·`as discussed`, 과거 화면·버그 해명, 폐기된 방식의 상세, 미사여구) → 지운다.
- **중복** → 정본 한 곳에 남기고 사본 결정은 지우지 말고 참조 한 줄로(`- PUB-7 [o] publish auth follows →=AUTH-3`). 결정 ID는 사라지지 않는다.
- **복제**(코드·다른 SSOT가 정본인 상세) → `→<ID>-n`이나 경로 한 줄.
- **이력·골격** → [x]는 한 줄, chg는 마지막 섹션. 골격 밖 섹션은 decisions로 흡수하거나 지우고 섹션 순서를 복원한다. chg 요약은 서술만 걷어낸다(ID 표기와 `old→new` 유지).
- **미분류 `→`** → 문장이 종류를 분명히 말할 때만 표시한다(`follows →X`·`as defined in →X`=정본 `→=`, 없으면 적용할 수 없는 조건=필수 `→!`, 화면·설명 위치만=관련 `→~`). 애매하면 두고 보고한다. `→!`·`→=`를 `→~`로 내리는 것은 gusta-update-ssot 거리다.
- **명확성 공백**(주체·범위·조건·예외·수치와 단위) → 채우지 않고 3절 보류.

**대조 검증 (편집마다, 확인 요청 전에)**: 원문에서 ① 조건 ② 예외 ③ 수치와 단위 ④ 부정(no·never·only) ⑤ 의무 수준(must·should) ⑥ 참조(→와 ! = ~)를 뽑아 편집본에서 하나씩 다시 찾는다. 하나라도 사라졌으면 되돌린다. 줄 수가 늘어도 괜찮다.
rev·chg·STATE pending은 건드리지 않는다.

신호가 없는 결정은 한 글자도 바꾸지 않는다. 결정 블록을 한 줄로 합치거나 경고를 없애려고 기계적으로 쪼개지 않는다(같이 바뀌는 정책은 한 결정). 다시 돌려 바뀌는 게 없으면 "변경 없음"이 정상이다.

## 3. 보류 — 고치지 않고 보고
조건·수치·부정·의무·범위가 달라지면 기획 변경이다. 다음은 그대로 두고 `gusta-update-ssot <ID>` 한 건으로 묶어 next에 남긴다: 서로 모순되는 두 결정(두 원문을 나란히, 정하는 건 사용자) · 조건·예외·수치가 빠진 공백(무엇이 빠졌는지만) · 뜻이 애매한 문장(원문과 물음만) · 현재 코드와 어긋나 보이는 결정(문서를 코드에 맞추지 않는다).

## 4. 마감
- git이 있으면 편집한 파일마다 `git diff -- spec/ssot/<ID>.md`로 결정 ID와 `[o]`/`[x]`/`[?]` 표시가 그대로이고 삭제된 줄의 수치·부정·참조가 편집본에 남았는지 확인한다(어긋나면 되돌리고 gusta-update-ssot로).
- 같은 `lint`를 다시 실행해 오류 0을 확인한다.
- `vibe log --text 'gusta-doc-review <IDs> tidied (rev unchanged)'`. 보류가 있으면 STATE next에 `gusta-update-ssot <ID>` 1줄.
- 보고(별도 파일 없음): ① 도메인별로 정리한 것(분할이면 `THEME-29 → THEME-29 + THEME-58..60`처럼 새 번호) ② 보류 — 원문 인용 한 줄씩 ③ 다음 단계(`gusta-update-ssot <ID>` 또는 남은 도메인).
